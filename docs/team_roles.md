# 6 人分工：一条 query 的一生

> 这份分工的唯一目的，是让每个人都有一段属于自己的模块、代码和故事。
> 我们不训练模型：下面所有交付都能在笔记本 CPU 加少量 API 调用下完成。
> 项目方案以 [PROPOSAL.md](../PROPOSAL.md) 为准，下文的"§"均指 PROPOSAL.md 的章节。
> 本文讲"做什么"，[tutorial.md](tutorial.md) 讲"为什么、怎么做"：所有人先读教程[第 0 章](tutorial.md#第-0-章全组必读)，再读自己角色那一章。

## 设计思路

项目本身是"循序渐进"的：先有标签体系，才有 `tag_search`；先有轨迹，才有奖励；先有奖励，才有优势。
如果按阶段排队，后面的人只能干等上游。这份分工用三个机制解决这个问题：

1. **竖切，不横切。** 每人认领一个完整阶段：读 PROPOSAL 对应章节、读懂对应的代码、做扩展、写测试、答辩讲那一段。
   不设"专门写文档""专门做 PPT"的角色，这类杂活作为每个人的"第二身份"分摊掉。
2. **替身先行，全员并行。** 仓库里每个上游产物都有现成的离线替身（`agentic_search.demo`），
   下游一开始就能开工，不用等上游。故事是串行的，干活是并行的。
3. **上下游互审成环。** 每人的 PR 由自己的直接下游 review（下游最关心接口能不能用），
   最后一环从数据回到标签体系，和 §4.2(2) 的数据飞轮是同一个闭环。

## 角色卡

### A 标签架构师："好内容从哪来"

- **先读**：教程[第 1 章](tutorial.md#第-1-章a-标签架构师)，可直接运行的例子包括：LUFFY 全 0 组示例、漏斗、标签树构建、准入阈值。必做项都能从这些例子改起。
- **必做**
  - 把玩具世界的标签树扩到至少 3 个 L1、6 个 L3（`demo.TREE_PATHS`），并给帖子补上标签路径。
  - 准备约 200 个兴趣点（手写或让 LLM 生成，故意混入同义词），跑 `run_funnel`，报告去重和聚类前后的数量。
  - 用 `AdmissionController` 设一组权重和阈值，写清楚为什么这么设。
- **加分**：用真实 LLM 实现 `Inducer` / `Reflector` 协议，跑一次自底向上归纳；
  用 `luffy_mixed_group_advantage` 画出"全 0 组被教师示范救活"的示意图。
- **答辩 3 分钟**：3000 万到 24 万的漏斗，以及三级树是怎么长出来的。

### B Agent 导演："一条 query 进门"

- **先读**：教程[第 2 章](tutorial.md#第-2-章b-agent-导演)，可直接运行的例子包括：回合解析、轮次预算兜底、动态 few-shot、Checkpoint 注入、接真实模型。必做项都能从这些例子改起。
- **必做**
  - 用 `OpenAICompatibleProvider` 接一个真实 API 模型作为策略（纯 prompt，不训练），在扩充后的语料上跑通至少 10 条 query。
  - 挑出 3 条好轨迹和 3 条坏轨迹（解析失败、轮次超限、跑题各一条），写一句话点评。
- **加分**：加一个"每轮只许发一个 query"的串行模式，和默认的横向并行对比平均轮次与耗时，复现 PROPOSAL 表 4 的趋势（4 轮/15 s 对 1~2 轮/6 s）。
- **答辩 3 分钟**：live demo，加上 Main Loop / Agent Once Loop / Checkpoint 三个概念。

### C 搜索管家："两条路去找帖子"

- **先读**：教程[第 3 章](tutorial.md#第-3-章c-搜索管家)，可直接运行的例子包括：级联路由、两个工具的调用、8 条 rollout 的流量风暴模拟。必做项都能从这些例子改起。
- **必做**
  - 把玩具语料扩到约 100 帖，从 `demo.py` 抽到 `examples/toy_corpus.jsonl`（`data/` 在 .gitignore 里），并写一个加载函数。
  - 给 `CascadeTagRouter` 补关键词表，统计 20 条 query 的路由命中率。
  - 用 `SearchProxy` 模拟 G=8 的并发风暴，报告请求合并率、缓存命中率和 QPS。
- **加分**：给 `community_search` 加"按时间衰减"的排序，构造一个"长青好帖被沉底、`tag_search` 能捞回来"的反例。
- **答辩 3 分钟**：为什么要双供给，以及训练时流量风暴的五层代理。

### D 裁判长："这条回答几分"

- **先读**：教程[第 4 章](tutorial.md#第-4-章d-裁判长)，可直接运行的例子包括：格式奖励判例、伪造引用、RaR 打分、出题格式。必做项都能从这些例子改起。
- **必做**
  - 出 20 到 30 条 mini benchmark：覆盖旅行、美食、影视、面试；包含硬约束、需要补查、检索无结果、需要澄清四类场景。每条写出 P0 约束和 rubric 细则。
  - 用 API 模型当裁判跑 `RaREvaluator`。
  - 给三类奖励各补 2 个对抗测试用例，提交到 `tests/`。
- **加分**：同一批轨迹用两个不同的裁判模型打分，统计一致率，看看 §4.3(1) 里"RM 与人类专家一致率 ≥95%"在小规模上是什么样子。
- **答辩 3 分钟**：10/30/60 奖励、P0/P1/P2 评分表，以及为什么一个 prompt 只评一个维度。

### E 优势分配官："分数怎么变成梯度"

- **先读**：教程[第 5 章](tutorial.md#第-5-章e-优势分配官)，可直接运行的例子包括：GRPO 优势、GSPO-token 等价、GiGPO 三轨迹算例、OPD 组合。必做项都能从这些例子改起。
- **必做**
  - "纸上 RL"：对 benchmark 里的每条 query，用 B 的设置采样 8 条轨迹，用 D 的奖励算出轨迹级 A^E 和 GiGPO 的步骤级 A^S。
    统计有多少步落在共享锚点组里，并画出"哪些步骤会被强化、哪些会被惩罚"。
  - 讲清 GiGPO 的状态与动作：状态是已持有的帖子集合，动作是 query（§4.3(2) 的界定）。
- **加分**：写一页"如果有卡怎么训"，逐个解释 `scripts/rl/` 的关键参数（3e-4/4e-4 裁剪、EP=8、n=8）；
  或用 `tests/test_losses.py` 讲解为什么 GSPO-token 与 GSPO 等价。
- **答辩 3 分钟**：一个分数如何变成每一步、每个 token 的信号。

### F 数据炼金师："数据飞轮，闭环收尾"

- **先读**：教程[第 6 章](tutorial.md#第-6-章f-数据炼金师)，可直接运行的例子包括：假日志挖掘、SFT 导出与掩码、pass@k 分流。必做项都能从这些例子改起。
- **必做**
  - 造一份假搜索日志（至少 30 个用户会话，包含同义改写和无关跳转），跑 `agentic-search mine-flywheel`，展示"怎么拆"和"何时不拆"。
  - 把 B 的好轨迹用 `export_sft_jsonl` 导出，标出哪些 token 计算 loss。
  - 用 E 的 8 次通过情况跑 `diagnose`，给每条 query 分流到 RL、SFT 或修系统。
- **加分**：用 `Checkpoint.with_injected_decomposition` 把挖到的子查询注入一条轨迹，再重新 rollout。
- **答辩 3 分钟**：数据飞轮和 badcase 回流，把整个故事收成一个环。

## 依赖与替身

谁也不用等谁：每个依赖现在就有替身可用。真实产物做好后，替换掉替身即可。

| 上游 → 下游 | 产物 | 现成的替身 |
|---|---|---|
| A → C | 标签树与带标签路径的帖子 | `demo.TREE_PATHS`、`demo.TAG_POSTS` |
| C → B | `tag_search` / `community_search` | `demo.build_registry()` |
| D → B、E | mini benchmark 里的 query | demo 中的成都 query |
| B → D、E、F | 真实 API 轨迹 | `demo.scripted_policy()` |
| D → E | 奖励函数 | `demo.rule_query_judge()`、`demo.rule_outcome_judges()` |
| E → F | 每条 query 的 8 次通过情况 | 手写的 `[True, False, ...]` 列表 |
| F → A | 按标签类目覆盖的 query 需求、空白标签样本 | 无需替身，用于下一轮迭代 |

**PR 互审环：A → C → B → D → E → F → A。** 每人的 PR 由环上的下一位 review。
另加一条跨环：E 顺带审 A 的 LUFFY 部分（两边都是 RL 数学）。

## 整体节奏

按四个阶段推进，前一阶段的产出就是后一阶段的输入：

1. **各自读懂**：读完自己的 PROPOSAL 章节与教程（第 0 章 + 自己的章），把教程里的代码跑一遍，跑通 `make check`；每人写一页"我的模块"，用教程每章末尾的自检问题检验自己。
2. **各自扩展**：完成角色卡里的必做项，全部基于替身完成。
3. **接力集成**：跑一次不训练的集成实验（见下文与教程[第 7 章](tutorial.md#第-7-章集成实验)），用真实产物替换替身。
4. **答辩**：PPT 统一风格，排练两遍，结题报告统稿。

每次组会由一人主持，按 A → F 轮换。主持人用 demo 演示"把我这一段接上之后的效果"。

## 集成实验：不训练也能做

PROPOSAL 的两张消融表（表 3 训练阶段递进、表 4 横向 Action 的时延收益）需要 GPU。
下面这组 prompt 级实验不需要训练，能给结题报告提供真实的数字。可运行的骨架代码在教程[第 7 章](tutorial.md#第-7-章集成实验)：

1. **双供给 vs 单供给**：只开 `community_search`，对比同时开两个工具，看 RaR 得分与引用准确率（C + D）。
2. **横向并行 vs 串行**：对比平均轮次和端到端耗时（B）。
3. **纸上 RL**：每条 query 采样 8 次，报告奖励方差、GiGPO 有信号的步骤占比，以及 pass@1 / pass@8（E）。
4. **badcase 分流**：按 pass@k 把失败 query 分到 RL、SFT、修系统三类（F）。

流水线是 D 出题 → B 采样 → D 打分 → E 算优势 → F 分流，A 和 C 负责供给侧的语料与标签。

## 参与感保底

- 每人至少 1 个合入的 PR（代码、测试、文档都算），至少 1 次 review。
- 每人答辩讲 3 分钟、负责 1 页主 slide，用自己的名字提交 commit。
- 结题报告每人写自己那一节，F 统稿，E 统一图表风格。

答辩顺序 A → B → C → D → E → F，共 18 分钟，B 在自己那一段做 2 分钟 live demo。
